# Auditoria ULTRA MÁXIMO — Arquitetura, Escala e Dívida Técnica Estrutural

> Redisparada em 2026-09-09 (Sonnet 5) para repor a rodada perdida no crash do VS Code.
> Complementar às auditorias `02-servicos-integracoes.md` e `08-infra-deploy-ci.md`; foco em
> decisões de longo prazo, não em bugs pontuais. Nenhum arquivo alterado.

---

## 1. Veredito arquitetural geral

O CRM foi construído com disciplina de engenheiro sênior no nível *tático* — RLS habilitada em toda tabela, RPCs atômicas para operações concorrentes (merge de fornecedores), interfaces limpas com factory para IA e email (`lib/ia/classifier.ts`, `lib/email/provider.ts`) — mas com **zero decisão explícita sobre o eixo que mais importa para os próximos 6-12 meses: se este é o CRM da Cavalcanti ou o CRM da Nogma**. O schema, o RLS, a camada de classificação por IA e a integração WhatsApp foram desenhados single-tenant de ponta a ponta, sem nenhum ponto de extensão (nem uma coluna `empresa_id` não usada) que sinalize a intenção de crescer para múltiplos clientes. Combinado com um terceiro tier de runtime — os workflows n8n — que carrega lógica de negócio (limiares de valor, cobrança automática, agregações financeiras) fora de qualquer controle de versão, revisão de código ou tipo, o sistema hoje é rápido de entregar e caro de generalizar: qualquer movimento em direção a multi-tenant, a um segundo canal de IA, ou a testes automatizados de verdade vai exigir retrabalho estrutural, não incremento.

---

## 2. Achados estruturais (por impacto de longo prazo)

### 2.1 — CRÍTICO: o schema e o RLS são single-tenant "por ausência", não por decisão

**Evidência:** `supabase/migrations/20260903100500_rls_policies.sql:44` — a política padrão para `obras`, `fornecedores`, `pagamentos`, `documentos`, `mensagens_whats`, `confirmacoes_pendentes` é `USING (auth.uid() IS NOT NULL)`: **qualquer usuário autenticado vê todas as linhas de todas as obras.** Não existe `empresa_id`, `cliente_id`, `construtora_id`, `organizacao_id` ou equivalente em nenhuma das 19 migrations (`grep -rn "tenant\|empresa_id\|organizacao" supabase/migrations/` → zero ocorrências) nem em `packages/db/src/types.ts`. Em `lib/services/classify-and-persist.ts:49-51`, o contexto passado ao classificador de IA é `obras.select('id,nome').eq('status','ativa')` — **todas** as obras ativas do banco inteiro, sem nenhum filtro por número de WhatsApp de origem, instância UAZAPI ou cliente.

**Por que isso importa:** não é um detalhe de segurança tratável depois — é a fundação. O dia em que a Nogma quiser rodar este CRM para uma segunda construtora, não dá para "ligar" isolamento: é preciso (a) adicionar coluna de tenant em ~8 tabelas, (b) reescrever as ~36 policies de RLS geradas pelo loop `DO $$ ... $$` de `rls_policies.sql:38-49` para incluir `AND empresa_id = current_empresa_id()`, (c) mapear "qual instância UAZAPI → qual empresa" em `app/api/webhooks/uazapi/route.ts`, (d) filtrar o contexto do classificador por empresa, (e) decidir se `profiles`/`categorias` são globais ou por tenant, e (f) migrar dados históricos assumindo que tudo pertence ao tenant "Cavalcanti". Cada mensagem de WhatsApp de um cliente futuro, sem essa mudança, hoje veria — em teoria, se o número não for filtrado antes — o contexto de obras de *outro* cliente. Isso é retrabalho de semanas em cima de um produto já em produção, não uma feature flag.

### 2.2 — ALTO: `packages/db` é um pacote de fachada — não existe fronteira real de domínio

**Evidência:** `packages/db/src/index.ts` tem uma linha: `export type { Database } from './types.js';`. `packages/db/package.json` só tem um script (`gen-types`). É puramente os tipos gerados pelo Supabase CLI. Toda a lógica de negócio — 14 módulos em `lib/data`, 5 em `lib/services`, classificador, providers de email, geração de PDF — mora dentro de `apps/web`. O `pnpm-workspace.yaml` declara `apps/*` e `packages/*`, mas há exatamente um app.

**Por que isso importa:** o monorepo *parece* preparado para múltiplos consumidores (um futuro app mobile, um worker separado para processar WhatsApp, um painel administrativo interno), mas na prática toda regra de negócio está amarrada ao runtime Next.js (`import 'server-only'` no topo de quase todo arquivo de `lib/`). Se amanhã for preciso um worker separado para processar mensagens do WhatsApp de forma assíncrona (o que a Seção 2.5 abaixo argumenta que vai ser necessário), a lógica de `classify-and-persist.ts` não pode ser reaproveitada como está — precisa ser extraída de dentro de `apps/web` para um pacote de domínio de verdade primeiro. A estrutura de monorepo hoje é cerimônia, não uma fronteira que está sendo de fato imposta.

### 2.3 — ALTO: lógica de negócio financeira vive em blobs JSON dentro de um markdown, fora de qualquer controle de versão

**Evidência:** `docs/N8N-COMPLETO.md` (1660+ linhas) contém os 7 workflows n8n como strings JSON coladas em blocos de código markdown. `grep -iln "n8n" --include=*.json` no repo inteiro não retorna nenhum arquivo `.json` de workflow versionado — eles só existem como texto dentro do `.md`. Dentro desses blobs há regras de negócio reais: `docs/N8N-COMPLETO.md:424` — `[IF: valor > 5000] → [Slack: post to #financeiro]` (limiar de alçada financeira hardcoded); `:888` — cobrança automática de fornecedor via WhatsApp após 7 dias sem nota fiscal; `:1148` — um `Code node` em JS puro fazendo agregação de pagamentos por status/obra para o resumo semanal, sem tipo, sem teste, sem revisão.

**Por que isso importa:** o TypeScript já tem seu próprio limiar de decisão financeira (`CONFIANCA_AUTO_APROVAR = 0.85` em `lib/services/classify-and-persist.ts:6`), e agora existe um **segundo** limiar de risco financeiro (`valor > 5000`) definido de forma completamente independente, num JSON dentro de um `.md`, sem relação estrutural com o primeiro. Nada impede que os dois divirjam silenciosamente. Pior: essa lógica não passa por `git diff`, não passa por PR, não é coberta por `pnpm typecheck` nem por lint, e sua única forma de auditoria é ler um documento de operação manualmente. Para um sistema que decide se um pagamento é auto-aprovado ou escalado, isso é dívida técnica de alto risco fiscal/contábil, não só de engenharia — e reverter (trazer essa lógica para dentro do código versionado, testável) fica mais caro a cada workflow novo que for colado nesse arquivo.

### 2.4 — MÉDIO-ALTO: autorização duplicada 5x — e o padrão vai precisar mudar quando o RLS ficar multi-tenant

**Evidência:** a função `assertAdmin()` está copiada, quase byte-a-byte, em `app/(app)/config/categorias/actions.ts:14-20`, `app/(app)/config/usuarios/actions.ts:19-30`, `app/(app)/config/webhooks/actions.ts:20`, `app/(app)/config/importar/actions.ts:9`, e uma variante `assertAdminOrGestor()` em `app/(app)/fornecedores/duplicatas/actions.ts:15`. Cada uma refaz independentemente: `auth.getUser()` → `select papel from profiles` → `redirect` se não bater. Não existe `lib/auth/guards.ts`. Adicionalmente, 10 arquivos diferentes (`lib/data/notificacoes.ts`, `lib/data/usuarios.ts`, `lib/services/classify-and-persist.ts`, `lib/services/detect-duplicates.ts`, `lib/services/dispatch-webhook.ts`, `lib/services/import-pagamentos.ts`, `lib/services/merge-fornecedores.ts`, `lib/storage/documents.ts`, e as duas rotas de API/cron) instanciam seu próprio client Supabase com service role diretamente, em vez de usar uma factory compartilhada.

**Por que isso importa:** isoladamente é só DRY. O que eleva a severidade é o cruzamento com o achado 2.1 — no dia em que a checagem de papel precisar virar "admin **da empresa X**" ou "gestor **da obra Y**", essa mudança tem que ser replicada manualmente em 6+ lugares (e, historicamente, esse é exatamente o tipo de mudança em que uma cópia fica desatualizada e vira um furo de segurança). Um guard único hoje custa uma tarde; encontrar e corrigir 6 cópias divergentes sob pressão, depois que o produto já tem dois clientes em produção, custa muito mais e é o tipo de bug que só aparece em auditoria de segurança.

### 2.5 — MÉDIO: nenhuma camada de fila/assincronia entre "mensagem chegou" e "IA processou" — o webhook *é* o processamento

**Evidência:** `app/api/webhooks/uazapi/route.ts:95` chama `await classifyAndPersist(row.id)` de forma síncrona, dentro da mesma requisição HTTP que responde ao UAZAPI (já apontado operacionalmente na auditoria 02, F-05). Do ponto de vista arquitetural, o desenho **não tem lugar nenhum** para inserir uma fila — não há tabela de outbox, não há Vercel Queue, não há Supabase Realtime/pg_cron consumindo uma tabela de pendências. `mensagens_whats.tentativas_reprocessamento` existe no schema (`...100300.sql:18`) mas nenhum código lê ou escreve nessa coluna (confirmado por grep).

**Por que isso importa:** com um provider de IA real (Anthropic) e um provider de WhatsApp real (UAZAPI), a latência composta de "webhook → IA → email → dispatch de webhooks" facilmente passa de alguns segundos. Isso não é só um problema de timeout (já coberto na auditoria 02) — é uma limitação estrutural: o sistema não tem onde colocar um retry inteligente, um dead-letter, ou um "processar em lote depois". Quando o volume crescer (mais fornecedores mandando mensagem ao mesmo tempo, ou um segundo cliente), a única alavanca disponível hoje é "aumentar o timeout da função serverless", que não escala. Introduzir uma fila depois que o webhook, o classificador e os efeitos colaterais (email, dispatch) já estão emaranhados numa função só (`classify-and-persist.ts`) é uma reescrita, não uma adição.

### 2.6 — MÉDIO: testabilidade tem um bom começo (interfaces de IA/Email) que o resto do código não segue

**Evidência positiva:** `lib/ia/classifier.ts:47-71` e `lib/email/provider.ts` implementam corretamente o padrão Provider + factory por env var — isso é testável por design. **Evidência negativa:** todo o resto da camada de dados (`lib/data/*.ts`, ex. `obras.ts:14`: `const supabase = await createClient()`) instancia o client Supabase *dentro* da função, em vez de recebê-lo injetado. Isso é consistente em ~44 pontos do código. Combinado com o achado já registrado na auditoria 08 (F-02: `vitest` não está nem instalado, zero testes unitários existem), o resultado é que a única forma de testar `listObras`, `classifyAndPersist` ou `detectDuplicates` hoje seria via mock de módulo (`vi.mock('@/lib/supabase/server')`), que é mais frágil e mais acoplado à implementação do que injeção de dependência simples.

**Por que isso importa:** o padrão bom já existe no código (Provider/factory) — o problema é que não foi generalizado para a camada de dados. Isso significa que qualquer refatoração de médio porte (e a Seção 2.1 já garante que uma virá) vai acontecer sem rede de segurança nenhuma. Quanto mais tempo passa sem essa fronteira de injeção existir, mais caro fica introduzi-la — cada novo módulo em `lib/data`/`lib/services` que segue o padrão atual é mais um lugar a refatorar depois.

### 2.7 — MÉDIO: custo de IA e de PDF não tem *nenhum* mecanismo de limite — e ele multiplica por tenant, não soma

As auditorias 02 (F-04, F-11) já quantificaram o custo por mensagem e por PDF hoje. O ponto arquitetural que falta: **não existe nenhuma primitiva de limite** no código — nem quota por tenant, nem cache de prompt, nem circuit breaker de custo. Isso é aceitável com um cliente porque o volume é baixo o suficiente para não doer. Mas é um problema estrutural porque, quando (não se) a Nogma abrir um segundo cliente, o custo de IA por mensagem não cresce proporcionalmente ao produto — ele já é O(nº de fornecedores) por mensagem *hoje*, e sem isolamento por tenant (2.1) e sem cache (2.6 da auditoria 02), cada cliente novo soma seu catálogo de fornecedores ao contexto de *todo* classificador, não só do seu. Resolver isso depois que o produto já tem tráfego real de dois clientes é infinitamente mais arriscado do que decidir a política de limite agora, com um cliente e volume controlável.

## 3. Recomendações de maior alavancagem (priorizadas)

1. **Decidir agora, por escrito, se multi-tenant entra no roadmap dos próximos 6-12 meses — e, se sim, adicionar a coluna de tenant hoje.** Mesmo que hoje só exista um valor possível (`empresa_id = 'cavalcanti'`), criar a coluna e o índice agora, enquanto o volume de dados é pequeno e o RLS pode ser estendido com um `AND` em vez de reescrito do zero, é ordens de grandeza mais barato do que fazer essa migração depois que houver dois clientes com dados reais e n8n workflows assumindo single-tenant. Esta é a decisão de maior alavancagem do relatório porque toda a Seção 2.1 depende dela.

2. **Extrair a lógica de negócio dos workflows n8n para dentro do código TypeScript versionado.** n8n deve ser transporte (webhook relay, agendamento), não o lugar onde mora o limiar de alçada financeira ou a lógica de agregação. Expor essas regras como endpoints HTTP internos chamados pelo n8n resolve, de uma vez, o risco de divergência com o `CONFIANCA_AUTO_APROVAR` do classificador, dá cobertura de teste, e faz esse código aparecer em `git diff`/PR novamente.

3. **Consolidar `assertAdmin`/`assertAdminOrGestor` num único `lib/auth/guards.ts`, e um único factory para o client Supabase com service role.** Baixo esforço, mas é o ponto de extensão necessário para quando a checagem de papel precisar considerar tenant/obra — fazer isso antes da migração multi-tenant é muito mais barato do que caçar 6 cópias divergentes depois.

4. **Instalar `vitest` (já sinalizado na auditoria 08, F-02) e, ao mesmo tempo, refatorar `lib/data`/`lib/services` para aceitar o client Supabase como parâmetro em vez de instanciá-lo internamente.** Fazer as duas coisas juntas é o que transforma "zero testes" em "arquitetura testável" — fazer só a primeira sem a segunda produz testes frágeis de mock de módulo que quebram a cada refactor.

5. **Antes de ligar `IA_PROVIDER=anthropic` em produção, introduzir uma fila/outbox mínima entre o webhook do UAZAPI e o processamento pela IA** (mesmo que seja só uma tabela + um cron a cada minuto, sem infra nova). Isso desacopla a resposta ao UAZAPI do tempo de resposta do classificador, fecha o ciclo do `tentativas_reprocessamento` que já existe no schema mas está morto, e evita que a arquitetura precise ser reescrita sob pressão quando o volume de mensagens crescer.
